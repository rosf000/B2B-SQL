# 00 — 資料庫閱讀指南

> **「給你一個陌生資料庫，你第一步做什麼？」**
> 工程師的答案不是 `SELECT * FROM customers`，而是先讀懂 Schema。

---

## 為什麼要學「讀資料庫」？

AI 可以幫你生成 SQL，但 AI 不知道：
- `customer_id` 在你的資料庫是不是真的唯一
- `deleted_at` 記錄的「刪除客戶」要不要排除
- 同一家公司有 3 個帳號，`company_id` 是哪一個才算數

**這些判斷需要你讀懂 Schema，AI 無法替代。**

---

## 五步驟讀懂陌生資料庫

### Step 1 — 列出所有 Table

```sql
-- PostgreSQL
\dt

-- 或
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;
```

拿到清單後，先問自己：
> 「這個資料庫的主題是什麼？它在追蹤什麼事情？」

---

### Step 2 — 找每張表的 Primary Key

```sql
-- 查看 customers 表的結構
\d customers

-- 或通用查法
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'customers'
ORDER BY ordinal_position;
```

**Primary Key 告訴你「這張表用什麼來識別每一列」。**

```
customers     → customer_id    （每一列是一個客戶）
orders        → order_id       （每一列是一筆訂單）
order_items   → order_item_id  （每一列是一個訂單中的一個商品）
```

---

### Step 3 — 找 Foreign Key（關聯）

```sql
-- 查詢所有 FK 關係
SELECT
    tc.table_name AS child_table,
    kcu.column_name AS child_column,
    ccu.table_name AS parent_table,
    ccu.column_name AS parent_column
FROM information_schema.table_constraints AS tc
JOIN information_schema.key_column_usage AS kcu
    ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage AS ccu
    ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY';
```

這會告訴你哪些表互相關聯。

---

### Step 4 — 畫出關係圖

```
Customer (1)
    │
    └─── Order (N)         ← 一個客戶有多筆訂單
              │
              └─── Order_Item (N)   ← 一筆訂單有多個商品明細
                        │
                        └─── Product (1)   ← 一個商品明細對應一個產品
```

**練習：不要用工具，用手畫出 M1 資料集的關係圖。**

---

### Step 5 — 最重要的問題：Data Grain

> **「這張表的一列，代表什麼？」**

這個概念叫 **Data Grain（資料粒度）**，是 SQL 分析最容易出錯的根源。

| Table | Data Grain（一列代表） |
|:---|:---|
| `customers` | 一個客戶 |
| `orders` | 一筆訂單 |
| `order_items` | 一筆訂單裡的一個商品 |
| `salespersons` | 一個業務員 |
| `products` | 一個產品 |

**為什麼 Grain 很重要？**

```sql
-- 問題：計算每個客戶的總營收
-- 錯誤寫法（JOIN 後 Grain 改變了）：

SELECT c.customer_id, SUM(o.amount) AS total_revenue
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id = oi.order_id  -- ⚠️ 這裡 Grain 變了！
GROUP BY c.customer_id;

-- 問題：每筆訂單有 3 個商品 → JOIN 後 orders 的每一列被重複 3 次
-- → SUM(o.amount) 會是三倍！
```

**每次 JOIN 之前，都要問：JOIN 之後，這張查詢的 Grain 是什麼？**

## 實戰：用五步驟讀 M1 資料集

對 `b2b_m1_sample.sql` 的資料庫做以下練習：

```sql
-- 練習 1：列出所有表
SELECT table_name FROM information_schema.tables WHERE table_schema = 'public';

-- 練習 2：查看每張表有幾列
SELECT 'customers' AS table_name, COUNT(*) FROM customers
UNION ALL
SELECT 'orders', COUNT(*) FROM orders
UNION ALL
SELECT 'order_items', COUNT(*) FROM order_items
UNION ALL
SELECT 'products', COUNT(*) FROM products
UNION ALL
SELECT 'salespersons', COUNT(*) FROM salespersons;

-- 練習 3：找出有沒有重複的 PK（理論上應該 0 筆）
SELECT customer_id, COUNT(*) AS count
FROM customers
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- 練習 4：找出 orders 有多少是「孤兒」（找不到對應客戶）
SELECT COUNT(*)
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;
```

## Schema Thinking 心智模型

```
拿到新 Database
    │
    ├─ 有哪些 Table？
    │
    ├─ 各 Table 的 PK 是什麼？
    │
    ├─ FK 關係是什麼？（誰連著誰？）
    │
    ├─ 每張表的 Grain 是什麼？
    │   （一列代表什麼業務實體？）
    │
    ├─ 有沒有「髒資料」的跡象？
    │   （NULL 太多？PK 有重複？FK 孤兒？）
    │
    └─ 這個資料庫設計要追蹤的業務問題是什麼？
```
